## 2026-03-23 — Ghostty shaders + View menu + /plan prompt

### Ghostty 1.3 changed config filename — script hardcoded old path `[id:W13-101][status:done:d0f5d275]`

**Pain:** `ghostty-shader.sh` assumed `config`, Ghostty 1.3+ uses `config.ghostty`. Silent failure.

**Why:** Hardcoded path, no version discovery.

**Fix:** Cascade fallback — try `config.ghostty` first, then `config`, then XDG. Lesson: version-dependent paths need ordered discovery.

### `fswatch` watcher dies immediately when spawned from `bash script.sh` `[id:W13-102][status:done:d0f5d275]`

**Pain:** `disown` doesn't survive non-interactive shell exit — child gets SIGHUP. Inline `bash -c` with complex quoting also fails silently.

**Why:** Non-interactive shells don't have job control; `disown` is a no-op.

**Fix:** Write watcher body to a temp script file, run with `nohup bash $tmpfile &`.

---

### `pgrep -x Ghostty` misses running process `[id:W13-103][status:done:d0f5d275]`

**Pain:** Check returned false even with Ghostty running.

**Why:** macOS app bundle name (`Ghostty`) ≠ binary name (`ghostty`).

**Fix:** `pgrep -xi` (case-insensitive).

### ID gaps from pre-assigned ranges confuse triage script `[id:W13-110][status:done:current]`

**Pain:** Blob1 used W12-001..016, blob2 started at W12-051. `cat: No such file or directory` errors for W12-017..050.

**Why:** Range buffers create intentional gaps. Script assumed contiguous IDs.

**Fix:** Added `[[ ! -f "$TMP/$id.status" ]] && continue` guard + `sort -t- -k2 -n` numeric sort.

### `xargs` breaks on backticks and quotes in descriptions `[id:W13-111][status:done:current]`

**Pain:** Triage script crashed on lines containing backticks.

**Why:** `xargs` interprets unmatched quotes as syntax.

**Fix:** Replaced `| xargs` with `| sed 's/^[[:space:]]*//;s/[[:space:]]*$//'`.

## 2026-03-23 — S1/S2 implementation + clipboard stretch

### `zodToJsonSchema` silently returns `{}` with Zod v4 `[id:W13-115][status:done:c7b3d958]`

**Pain:** `ghostty.shader.set` showed `params: {}` — arg schemas weren't surfacing despite Zod schemas existing in catalog.

**Why:** `zodToJsonSchema` library is incompatible with Zod v4. It doesn't throw — it returns `{}` silently. Three iterations debugging before finding the root.

**Fix:** Zod v4 has native `.toJSONSchema()` on every schema object. `(def.params as any).toJSONSchema?.()` replaces the library call.

#### → Ideas
- Audit other `zodToJsonSchema` call sites — there may be more silent `{}` returns elsewhere `[id:W13-009][status:open]`

---

### `wibwob` is a compiled Bun binary — CLI source changes don't live-reload `[id:W13-116][status:done:current]`

**Pain:** Edited `wibwob.ts` human-readable output, restarted TUI, changes didn't appear. Took a beat to remember the binary is pre-compiled.

**Why:** `wibwob` at `/usr/local/bin/wibwob` is a compiled binary. Source changes in `src/cli/wibwob.ts` only land after a rebuild + reinstall.

**Fix:** Server-side changes (command-registry, control-api) take effect on TUI restart. CLI rendering changes need a rebuild. Note this in PRD AC.

## 2026-03-23 — S3/S4 implementation

### S3 health gate uses curl subprocess — slightly inelegant `[id:W13-118][status:partial]`

**Pain:** To check screen size before dispatch, we spin up a `curl` process per instance via `childProcess.spawnSync`. The CLI already has an async `api()` function for HTTP-over-unix-socket but it's async and `resolveBase()` is sync.

**Why:** Sync/async mismatch. The resolution chain is synchronous; doing a proper HTTP call would require refactoring the entire CLI entrypoint to async.

**Fix:** Works fine for now. Long-term: make `resolveBase()` async so it can use the existing `api()` infrastructure.

#### → Ideas
- Make `resolveBase()` async — lets S3 health gate use `api()` instead of curl subprocess `[id:W13-011][status:open]`
