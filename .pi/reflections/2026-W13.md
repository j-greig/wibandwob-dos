### Ghostty 1.3 changed config filename — script hardcoded old path `[id:W13-101][status:done:d0f5d275]`

### `fswatch` watcher dies immediately when spawned from `bash script.sh` `[id:W13-102][status:done:d0f5d275]`

### `safeSetStyle` track crash on theme cycle `[id:W13-210][status:done:3c5f6042]`

**Pain:** Theme cycling with multiple windows open (primer browser + figlet + file manager) crashed with `TypeError: undefined is not an object (evaluating 'this.style.track.fg')` in blessed's render loop.

**Why:** `safeSetStyle` only checked `el.scrollable` (a property set at creation time) to decide whether to inject `track`/`scrollbar` sub-styles. Many blessed elements are functionally scrollable but don't expose `.scrollable` as a live JS property — they just had those sub-styles in their original style object. When `restyleAll` called `safeSetStyle`, it stripped `track`, blessed tried to render the scrollbar and crashed.

**Fix:** `safeSetStyle` now also checks `el.style?.scrollbar` and `el.style?.track` — if the element *had* these before, it always gets them back. Also fixed `restyleAll` to not spread `...window.frame.style` wholesale (only preserve `border`).

**Fix (also):** Noted in GOTCHAS.md under the existing blessed list crash entry.

---

### Theme cycle visual proof ✓

**Theme cycling worked correctly after the fix** — all 6 variants (dark, dark-pastel, dark-nord, monochrome-dark, phosphor, light) cycled with 0.5s pauses across 3 open windows (primer browser, figlet, file manager) without crash. Confirmed visually via `scripts/ghostty-capture.sh --port`.

## 2026-03-24 — style.track root cause + SDK gap

### Partial fix let the same crash recur for 7 days `[id:W13-220][status:done:0e54007e]`

**Pain:** `TypeError: undefined is not an object (evaluating 'this.style.track.fg')` kept coming back across multiple sessions despite the W13-210 fix to `safeSetStyle`.

**Why:** The W13-210 fix hardened detection inside `safeSetStyle` but never fixed the call site. `figlet-banner/index.ts` creates viewer elements with `scrollbar.track` (which causes blessed to set `this.track` on the widget), then in `onRestyle()` does `viewer.style = nt.body` — direct replacement, bypassing `safeSetStyle` entirely. No amount of improving `safeSetStyle` helps if you never call it.

**Root structural cause:** `safeSetStyle` was never exported from `microapp-sdk.ts`. Microapp authors had no COAT-compliant path to use it. The natural, obvious pattern is `el.style = host.theme().body` — and that pattern is silently fatal for scrollable elements with `scrollbar.track` set. The architecture said "implement `onRestyle()`" but didn't give you the safe tool to do so.

**Fix:**
- `safeSetStyle` exported from the SDK
- `safeSetStyle` also checks `(el as any).track` (blessed widget property) — survives even if `el.style` was already wiped once before
- `figlet-banner`: two `viewer.style = nt.body` → `safeSetStyle(viewer, nt.body)`
- `SDK-MICROAPP-DEV.md`: documents the BAD/GOOD pattern explicitly

**Lesson:** When a fix doesn't stick, ask whether the fix was applied to the symptom (the utility) rather than the cause (the call site). Also: the right tool not being on the SDK surface is as bad as the tool not existing — authors can't use what they can't reach.

#### → Ideas
- Audit all `el.style =` direct assignments in microapps for scrollable elements — there are ~40 across the codebase, most are safe (no `scrollbar.track`) but future microapps will repeat this `[id:W13-221][status:open]`
- `composition-helpers.ts` `createTextViewer` should expose a `restyle()` method that calls `safeSetStyle` internally — then `onRestyle` becomes `() => viewer.restyle()` with no blessed knowledge needed `[id:W13-222][status:open]`
