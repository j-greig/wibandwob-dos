### blessed.list style.item crash on theme switch
- blessed internally accesses `self.style.item[name]` and `this.style.scrollbar.fg`
- When `restyleAll` sets `listBox.style = { ...th.body, selected: {...} }` without `item` or `scrollbar`, blessed crashes
- Fix: always include `item: { fg, bg }` and `scrollbar: { fg }` in list style AND in onRestyle handler
- Same applies to any scrollable blessed.box — needs `scrollbar` in style during restyle

### renderMarkdown vs plain text body
- `renderMarkdown()` treats each line as a paragraph → adds blank lines between them
- ASCII art bodies (ZILLA) rendered with inter-line gaps
- Fix: `hasMarkdown()` regex detects `##`, `- `, ``` etc — only use renderMarkdown for actual markdown
- `renderBody()` dispatches: markdown→renderMarkdown, plain→wrapText

### Figlet window ID capture is broken in all cinema scripts

**Every choreography script gets this wrong.** When you open a figlet via
`figlet.open`, the window's `.kind` is `"microapp"`, not `"figlet"`. So this
jq query returns nothing:

```bash

$W windows | jq -r '[.[] | select(.kind=="figlet")][-1].id'
```

The fix is to match on `.appType`:


## 2026-03-15 — WibMux Ghost Cursor: clicking the TUI from code

### Discovery: Ghostty AppleScript has `send mouse position` + `send mouse button`

Ghostty 1.3's SDEF exposes three mouse commands:

```
send mouse position x <pixels> y <pixels> to <terminal>
send mouse button <left/right/middle button> action <press/release> to <terminal>
send mouse scroll x <delta> y <delta> to <terminal>
```

**Pixel coordinates are relative to the terminal surface**, not the macOS window frame.
This means we can compute click targets from blessed's cell grid:

```
pixel_x = column * cell_width    (cell_width ≈ 8px at default font-size 13)
pixel_y = row * cell_height      (cell_height ≈ 17px at default font-size 13)
```

### Proof of concept: clicking TUI menus via AppleScript

Opened the "Core Apps" menu by ghost-clicking the menu bar:

```applescript
tell application "Ghostty"
    set t to first terminal of front window
    -- "Core Apps" starts at column ~35 on the menu bar (row 0)
    -- Pixel: 35 * 8 = 280, row 0 center = 8
    send mouse position x 280 y 8 to t
    delay 0.1
    send mouse button left button action press to t
    delay 0.05
    send mouse button left button action release to t
end tell
```

**Verified via API:** `GET /state` → `{"menu": {"open": true, "label": "Core Apps"}}`
**Verified via screenshot:** dropdown visible with Command Lab, Contour Studio, etc.

Then closed it and opened "Help" the same way:

```bash
# Find position: grep -bo "Help" on first line of screenshot/text → byte offset 57
# Pixel: col 60 * 8 = 480, row 0 = 8
send mouse position x 480 y 8 to t
send mouse button left button action press to t
send mouse button left button action release to t
```

**Both worked first try.** Blessed receives these as genuine mouse events — the exact
same code path as a human clicking. No keyboard shortcut simulation, no API bypass.

### How to find click targets

1. `curl -s http://127.0.0.1:8099/screenshot/text | head -1 | grep -bo "Label"` → column offset
2. Column × 8 = pixel X, row × 17 = pixel Y (approximate, default Ghostty font)
3. For window-relative targets, read window position from `/state` and add offsets

### Cell-to-pixel calibration

The ~8×17 ratio works for default Ghostty (font-size 13, Menlo/SF Mono).
Different fonts or font sizes will need recalibration. Could be auto-detected:
- Open a 1×1 test window at known position
- Read pixel dimensions from Ghostty AppleScript window bounds
- Divide by terminal columns/rows from `/state`

### What this enables

- **Automated UI testing without a human.** Click menus, open windows, navigate
  file browsers, interact with form fields — all via the PTY, exercising the
  real blessed mouse event path.
- **Ghost user test scripts.** Choreographed sequences that drive the full TUI
  stack: menu → select item → verify window opened → interact with content.
- **WibMux `click` command.** `wibmux click --col 35 --row 0` with auto
  cell-to-pixel conversion.

### Recipe (copy-paste ready)

```bash
# Step 1: Find where a label sits on screen
COL=$(curl -s http://127.0.0.1:8099/screenshot/text | head -1 | grep -bo "Help" | cut -d: -f1)

# Step 2: Convert to pixels (default Ghostty font)
PX=$((COL * 8))
PY=8  # row 0, vertically centered

# Step 3: Ghost-click via Ghostty AppleScript
osascript -e "
tell application \"Ghostty\"
    set t to first terminal of front window
    send mouse position x $PX y $PY to t
    delay 0.1
    send mouse button left button action press to t
    delay 0.05
    send mouse button left button action release to t
end tell"

# Step 4: Verify
curl -s http://127.0.0.1:8099/state | python3 -c "import sys,json; print(json.dumps(json.load(sys.stdin)['menu']))"
```

- `autoresearch/wibmux/wibmux.sh` — existing wmux CLI (has `cmd_click` for macOS screen coords via System Events, but this new approach clicks *inside the terminal surface*)
- `autoresearch/wibmux/ghost-user-test.sh` — WIP test script using HTTP API (needs migration to ghost-click approach)

Swept all 7 menus: File → Edit → View → Window → Core Apps → Applications → Help,

**The primitive for any future agent:**

```bash
ghost_click() {
```

### window.close silently accepts wrong args — agent confusion

**Bug:** `wibwob cmd window.close --windowId 7` returns `{"ok": true}` but does NOT

#### Mouse drag — FIXED

**Root cause:** Terminal sends repeated `mousedown` events during a drag, NOT
`mousemove`. Built a standalone test (`/tmp/drag-test.ts`) that proved this —
154 events, all `action: "mousedown"` with changing x,y coordinates.

**The fix (one line):** In the program-level drag handler, check for
`data.action === "mousedown"` instead of `data.action === "mousemove"`.

**Architecture that works:**
1. `screen.on("mouse")` — handles initial mousedown (start drag) and mouseup (end drag + save)
2. `screen.program.on("mouse")` — handles drag motion at raw level, bypasses blessed element routing
3. Screen handler sets `dragging` state, program handler moves the panel while `dragging` is set
4. On mouseup, position saved to YAML with selfWriteFlag to prevent file-watch reload

**Key blessed discovery:** `host.screen.program.on("mouse")` is the raw event
stream from the terminal. `host.screen.on("mouse")` goes through blessed's
element routing which can swallow events. For drag, you need program level.

## 2026-03-19 — blessed-contrib Widget Rendering: Codex Diagnosis of a "Black Hole" Bug

**What happened:** Built `microapps/demo-dashboards-v2/` — a combined dashboard microapp merging two disabled sources. The window opened, state showed correct dimensions, the `tick` counter incremented every second — but `GET /screenshot/ansi?id=N` returned only `{bg} ` (one background-color cell), and all the `blessed-contrib` widgets (line, bar, donut, gauge, sparkline, log) rendered completely blank.

**Symptoms:**
- `wibwob state` shows window with correct dimensions and `tick: N` incrementing
- `GET /windows/text?id=N` returns `captureText` fallback text only
- `GET /screenshot/ansi?id=N` returns only the viewport background cell (one line, one color)
- No errors in the app log
- `describeState()` fires correctly every second
- Widget boxes visibly occupy space (borders visible) — only content is invisible

---

### 5 Whys (Root Cause Chain)

**Why 1 — Why did the contrib widgets render blank?**
→ Because `blessed-contrib` canvas widgets (line, bar, donut, gauge) allocate their internal drawille (braille-pixel) canvas on `attach`, using whatever `width`/`height` they have at attach time. If `width` was 0 or undefined at attach, the backing canvas is 0×N or tiny, and the content paints into the wrong buffer.

**Why 2 — Why did widgets attach with zero/undefined dimensions?**
→ The microapp created widgets as standalone children of a `blessed.box` container, then called `applyRect()` to set their position/size. But `applyRect()` sets blessed properties AFTER creation — the `attach` event (when blessed adds the widget to the screen) fires at widget creation time, before `applyRect()` ever runs. At creation, `widget.width` was `undefined` → attach-time `calcSize()` computed `0×N` → drawille canvas was tiny.

**Why 3 — Why were widgets created before layout ran?**
→ In the original grid-based approach, widgets were created immediately in the `action()` callback (synchronous). But the screen was 1×1 (headless/background mode) at that moment, so `contrib.grid` threw "Width must be multiple of 2!" — which is why we switched to standalone widgets. The standalone approach avoided the immediate crash but reintroduced the attach-time sizing problem.

**Why 4 — Why did the screen report 1×1 at widget creation time?**
→ When `wibwob cmd microapp.wibwob.demo-dashboards-v2.open` runs, it calls into the microapp's `action()` callback synchronously. The window exists but the shell (header + tabStrip + viewport layout) hadn't rendered yet. The window body's `width`/`height` was not yet set from the actual terminal dimensions. In headless/background mode the screen can report 1×1.

**Why 5 — Why did the render loop (1-second timer) not fix it?**
→ Once `render()` finally ran with real dimensions and called `applyRect()`, the widgets' blessed properties were updated. But the canvas widget's internal drawille canvas was already allocated at the tiny attach-time size. `applyRect()` only sets blessed position properties — it does NOT tell the canvas widget to re-allocate its backing store. The canvas widget kept the tiny canvas dimensions.

**Root cause (summary):** `blessed-contrib` canvas widgets allocate their backing drawille canvas at attach-time using whatever blessed dimensions exist then. In our microapp, widgets attached before layout gave them real dimensions. Subsequent `applyRect()` calls updated blessed properties but not the internal canvas. The result: invisible content, correctly-sized borders.

---

### How Codex Fixed It (Three-Change Patch)

Codex identified the attach-time sizing problem precisely. Applied three changes:

#### Change 1: `applyContribRect()` — signal resize after layout

In `microapps/demo-dashboards-v2/index.ts`, replaced `applyRect()` with a wrapper that emits a `resize` event after setting blessed properties:

```typescript
function applyContribRect(
  widget: any,
  rect: { top: number; left: number; width: number; height: number },
) {
  applyRect(widget, rect);
  if (widget && typeof widget.emit === "function") {
    widget.emit("resize");
  }
}
```

All contrib widget layout calls now use `applyContribRect()` instead of bare `applyRect()`.

#### Change 2: `canvas.js` — `syncCanvas()` + `resize` event handler

In `node_modules/blessed-contrib/lib/widget/canvas.js`:

**Added `syncCanvas()` method** — detects when blessed dimensions changed since last canvas allocation, re-allocates the drawille canvas, and returns `true` if resize happened:

```javascript
Canvas.prototype.syncCanvas = function(force) {
  this.calcSize();
  this.canvasSize = this.canvasSize || { width: 0, height: 0 };
  var sig = this.canvasSize.width + 'x' + this.canvasSize.height;
  if (!force && this.ctx && this._canvas && this._canvasSig === sig) {
    return false; // unchanged
  }
  this._canvas = new InnerCanvas(this.canvasSize.width, this.canvasSize.height, this.canvasType);
  this.ctx = this._canvas.getContext();
  this._canvasSig = sig;
  return true; // resized
};
```

**Added `resize` event handler** — listens for blessed `resize` events and re-syncs the canvas:

```javascript
this.on('resize', function() {
  var resized = self.syncCanvas();
  if (resized && self.currentData && typeof self.setData === 'function') {
    self.setData(self.currentData);
  }
});
```

**Updated `attach` handler** to call `syncCanvas(true)` instead of inline logic.

**Updated `render()`** to lazy-init canvas if needed:

```javascript
Canvas.prototype.render = function() {
  if (!this.ctx) {
    this.syncCanvas(true);
  }
  // ... unchanged rest
};
```

#### Change 3: `line.js` — `currentData` cache for resize repaint

In `node_modules/blessed-contrib/lib/widget/charts/line.js`:

`setData()` now stores data as `this.currentData` (already was doing this for legend, but Codex ensured it's always set):

```javascript
Line.prototype.setData = function(data) {
  if (!this.ctx) { throw 'error: ...'; }
  if (!Array.isArray(data)) data = [data];
  this.currentData = data; // cached for resize repaint
  // ... rest of drawing logic
};
```

Combined with the canvas `resize` handler, this means: when `applyContribRect()` fires `resize` → `syncCanvas()` re-allocates canvas → `setData(currentData)` repaints from the cached dataset.

---

### Architectural Implication

This is a **node_modules patch** — `canvas.js` and `line.js` in `node_modules/` are now modified. These changes will survive `bun install` only if:
1. The dependency is locked (`bun.lockb`)
2. No fresh `node_modules` install happens (e.g. after `rm -rf node_modules`)

**Proper long-term fix options:**
1. **Fork blessed-contrib** and publish a patched version to npm (or a private registry)
2. **Postinstall patch script** — `scripts/patch-blessed-contrib.js` that applies the same diff after every `bun install`
3. **Upstream the fix** — file a PR with the `resize` event handler and `syncCanvas()` pattern

The `syncCanvas()` pattern is the correct fix — it's a legitimate bug in blessed-contrib (canvas widgets should observe blessed dimension changes and re-allocate, but they don't by default).
