## TL;DR verdict

The plan is right in direction but has a priority inversion.
**Sessions 1 and 3 (tooling gate + generated docs) are correct.**
**Sessions 2, 4, 5 are real work but miss the higher-leverage thing visible in the
shell docs that the plan doesn't address yet.**

The higher-leverage thing: **`app-controller.ts` is 2313 lines and `file-manager-window.ts`
is 1859 lines, but the architectural invariants explicitly prohibit what's causing
those numbers.** The health gate (Session 1) will catch symptoms. The invariants
already name the cures. Those two things need to be connected more directly.

## What the shell docs reveal that the spike plan doesn't mention

### 1. The invariant doc names the anti-patterns we're still committing

`invariants.md` rule 9: "Services own logic, windows own wiring."

`app-controller.ts` has 2313 lines. The architecture doc explicitly says it
"should continue decomposing into focused window families." The invariant doc
calls out "giant controller growth when a window family or service can be
extracted cleanly" as an explicit anti-pattern.

The spike plan addresses music-player migration (Session 5) — one file.
But the architecture doc says `app-controller.ts` itself is the known rough edge.
Neither spike mentions it. It's the source of the most ongoing architecture debt.

**What to add to the spike:** a Session 0.5 or a note in Session 1 — after
`health-full.sh` passes, run `wc -l src/core/app-controller.ts` and track it
as a secondary metric. The gate should surface it. The sprint after this one
should target it explicitly.

### 2. The integration surface is auto-generated — we should be doing the same

`integration-surface.md` has this at the top:
> "Auto-generated by `scripts/checks/gen-integration-surface.ts`.
> Do not edit by hand. Regenerate: `bun run scripts/checks/gen-integration-surface.ts`"

This already exists. The spike plans to build `sdk-export-index.sh` as a new
generated doc. But the pattern is already proven in this repo — the integration
surface (23 endpoints, 85 commands) regenerates from code. The SDK export index
is the same idea applied to `microapp-sdk.ts`.

**Implication:** Session 3 (generated SDK index) isn't introducing a new pattern —
it's extending an existing one. The implementation should mirror
`gen-integration-surface.ts` not reinvent from scratch. Read that script before
writing the new one.

**Also:** `bun run scripts/checks/gen-integration-surface.ts` should be in
`health-full.sh` alongside knip and madge. If the integration surface is stale
vs the live API, that's a doc-drift failure the gate should catch.

### 3. The W12 reflection is a direct brief for the spike — but the spike doesn't cite it

W12 documents real pain:
- **Instance confusion / ghost sockets** → fixed by control manifest (S1 ✅)
- **`microapps.reload` half-state** → fixed by reload invalidator (S2 ✅)
- **"where did the stacktrace go?"** → fixed by crash-bundle (S3 ✅)

But W12 also documents pain we haven't addressed:

> "SDK focus theft" — microapps can steal keyboard focus from the desktop
> and not return it cleanly on close.

> "blessed mouse/keyboard pain" — `element.key()` registers globally on program,
> not per-element. 2-3x fire per keystroke. Wrong element targeted during scroll.

> "contour resize failed silently — returned false for resize, then closed itself"

These are **active reliability issues** in the running app right now. None of them
appear in the spike plan. The health gate (Session 1) won't catch them because
they're runtime behavioural bugs, not static analysis issues.

**What to add:** a Runtime Behaviour section in the spike with the W12 bugs as
named items. Flag which ones need fixes vs which need docs in pitfalls.md.
Focus theft and key.() double-fire in particular recur across microapps — they
deserve a pitfalls.md entry and possibly a composition-helpers mitigation.

### 4. `describeState()` is the agent parity seam — but completeness varies wildly

Invariant 12: "User-visible surfaces must be API-visible."
Invariant 5: "Every window type must expose semantic metadata through `describeState()`."

The architecture doc says: "If an agent needs a property, add it to the window
metadata contract rather than teaching the agent to scrape UI text."

From the W12 reflection, the session involved `wibwob read`, `wibwob state`, and
`wibwob map` constantly — these are all downstream of `describeState()`.
But compliance is inconsistent. Some microapps return `{ summary: "..." }` and
nothing else. The hero 7 effort (Session 2) partially addresses this for reference
apps but doesn't address the broader fleet of 44 microapps.

**What to add:** `microapp-smoke.sh` (planned in Session 2) should check that each
microapp's `describeState()` returns at minimum:
- `summary` (non-empty string)
- `appType` (present and matching the microapp id)
- at least one semantic field beyond summary

Exit 1 if any hero app fails. Warn (not fail) for the broader fleet.

### 5. The COAT test is binary and strong — the spike should use it

From `AGENTS.md`:
> "The COAT test: Would this work without the TUI, using only the API?"

Every piece of work in this spike should be able to answer "yes" to the COAT test.

Looking at the plan:
- `health-full.sh` — runs from CLI, no TUI. ✅ COAT-aligned.
- Hero 7 validation — needs `wibwob cmd`, `wibwob read`, `wibwob state`. ✅ COAT-aligned.
- `sdk-export-index.sh` — generates a doc from source. ✅ COAT-aligned.
- Infra wrappers — code change. ✅ COAT-aligned.
- Music player migration — adds `microapp.wibwob.music-player.open` to the

But: the Session 2 acceptance test says "open → describeState → captureText →
close each." Make that explicit in the script. Don't accept "it opens" as proof.
Require `wibwob read <id>` returns non-empty text. That's the COAT bar.

### 6. The agent tools surface is often the forgotten COAT gap

`agent-native.md` principle 1: "Whatever the user can do through the UI, the agent
must be able to achieve through tools."

`agent-native.md` principle 4: "Agent can accomplish things you didn't explicitly
design for."

Right now, `wibwob crash-bundle` collects evidence but nothing in the app can
auto-detect a crash and call it. The agent has to notice the instance is gone,
run the bundle manually, and reason from it.

The gstack equivalent is: version check on every invocation → auto-kill stale
server. We have the pieces (control manifest + reload invalidator) but no
automation that acts on them.

**Sketch of what "COAT-complete crash recovery" looks like:**
```bash
# In health-full.sh or a new script:
if ! bun run wibwob health > /dev/null 2>&1; then
  echo "⚠ instance not responding — collecting crash bundle..."
  bun run wibwob crash-bundle --out scratch/reports/crash-$(date +%Y%m%d-%H%M)
  echo "Bundle saved. Restart: tmux send-keys -t wibwob 'bun run dev:world' Enter"
  exit 1
fi
```

Not complicated. Closes the loop from "instance dead" to "evidence collected +
restart instruction" in one command. The skill preamble pattern from gstack
(check runtime, warn if stale) is exactly this.

### 7. The `wibwob-session-briefing.sh` idea is the real win

Sketched in the gstack deep-dive as a future script that combines:
- `wibwob status` (instance alive + identity)
- open todos count
- active spike name + status
- usage-pulse maturity signal

This directly solves the W12 pain of "what state are we in?" at session open.
It's also more valuable than knip output to most agents. An agent that knows
"we're 3 sessions into a spike, 2 todos open, 1 assigned to this session, and
the instance is 4af at 159×54" can start delivering immediately.

**Move this to Session 1 scope**, or make it Session 0 (runs in < 30 seconds,
no dependencies beyond `wibwob` and `find`). It's simpler than `health-full.sh`
and more immediately useful.

## What the plan gets right — keep it

- **gstack adaptation strategy** is sound. Generate don't hand-write, preamble
  pattern for skills, JSONL for analytics. All of this is the right direction.
- **Session ordering** (gate first, then validated examples, then generated docs)
  is the correct dependency order.
- **Triad agent model** (product-owner → developer → doc-refiner) worked in the
  last sprint and should be the default for any implementation slice.
- **"Boil the Lake" framing** for the 24 raw fs calls and infra wrappers is right.
  These are lakes, not oceans. The marginal AI cost is near-zero. Do them.
- **usage-pulse data maturity caveat** — correct to wait 1 week before drawing
  fleet conclusions. Don't consolidate skills on day-1 data.

## The thing that isn't said anywhere in the docs but should be

The reflections (W11, W12) are the most honest signal in this codebase about
what's actually painful. They name specific bugs, specific friction, specific
ideas. But they're not fed back into the planning system in any structured way.

W11 identified `element.key()` double-fire as a recurring issue across microapps.
That's now in W12 and probably in W13. It's not in pitfalls.md. It's not in
invariants.md. It's not in the spike plan.

The gstack equivalent is the retro skill writing to `~/.gstack/projects/<slug>/`
so that `/ship` picks it up. Our reflections are isolated markdown files that
require a human to read and promote.

**The missing link:** a lightweight process where friction documented in
`reflections/2026-Wnn.md` automatically populates a `pitfalls.md` candidate
section during the next session. Could be as simple as:

```bash
# In wibwob-session-briefing.sh:
LATEST_REFLECTION=$(ls .agents/reflections/2026-W*.md | sort | tail -1)
echo "Latest reflection: $LATEST_REFLECTION"
OPEN_ITEMS=$(grep -c '^\*\*Fix' "$LATEST_REFLECTION" 2>/dev/null || echo 0)
echo "  Open fix items: $OPEN_ITEMS"
```

Not a requirement for the spike. But it closes the loop between "what hurt last
week" and "what we build this week."
