# Plumbing Text Between Windows — Plan 9 in a TUI

We just ran a four-window plumb circuit inside WibWob-DOS that proves the core thesis: every window is a file you can read from and write to. A chaos primer (10 lines of unicode box-drawing art) sat in window 3. `wibwob plumb --from 3 --to 4` captured its text via the `/screenshot/text` endpoint — which prefers each window's semantic `captureText()` over a raw screen scrape — and dispatched it to the notepad's `write` command via `/commands/run`. No new API endpoints, no new SDK methods: just the existing read and write seams composed. The notepad received 175 bytes of clean unicode, rendered it without wrapping (`wrap: false`), and became a buffer we could plumb onward. `wibwob plumb --from 4 --to 2` hit the Wib&Wob agent chat via `agent.send` — a host-window fallback the CLI discovers by stripping the `wibwob-` prefix and searching the command catalog. The agent *read the art*, called it "a descending spiral, quite elegant," then we plumbed its 1,784-character response back out to a fourth notepad in the bottom-right. Four windows, three plumbs, zero new infrastructure. This is Plan 9's `plumb(1)` philosophy — text flows between programs through a uniform interface — except the programs are overlapping TUI windows sharing a blessed screen, and the plumber is a 60-line CLI function that composes two existing HTTP calls.
