## Chain of thought (unfiltered)

Trying to parse what the user is actually pointing at. Three distinct threads:

**Thread 1: The system itself**
The gen scripts declare their own metadata (`@watches`/`@output`/`@run`). Their outputs link back to their generators (`<!-- AUTO-GENERATED by X -->`). AGENTS.md describes the system that maintains AGENTS.md. doc-sync.sh discovers participants automatically — nobody has to register them manually. The system produces, describes, and regenerates itself. What's the name for that?

Went hunting through existing concepts:
- Literate programming (Knuth) — prose and code woven together, but one-directional. Code explains prose. Prose doesn't point back to code that generated it.
- Living documentation (Swagger/OpenAPI) — generated from code, but the link is one-way. The output doesn't know its generator.
- Homoiconicity (Lisp) — code is data is code. The system can inspect and modify itself. Closer but about runtime, not documentation.
- Second-order cybernetics — systems that observe themselves. Closer in spirit.
- Self-hosting compilers — compilers that compile themselves. Analogous but about execution not documentation.

The closest formal concept is **autopoiesis** — coined by Maturana and Varela in biology. A system that continuously produces and maintains the components that constitute it. A cell is autopoietic. The WibWob-DOS doc system is autopoietic: gen scripts produce outputs → outputs declare their generators → generators declare their watches → doc-sync discovers generators → AGENTS.md describes all of it → agents reading AGENTS.md can reproduce the whole system.

The two-way linking is the key non-obvious thing. Most doc systems are open-loop: code changes, you manually update docs, nobody enforces it. This is closed-loop: the output knows who made it, the maker declares what it watches, a script closes the feedback loop automatically.

Best term: **reflexive documentation**. The doc system reflects on itself — it contains the instructions for its own maintenance and regeneration. The word "reflexive" captures: (1) self-referential, (2) the outputs point back to their sources, (3) the system can be reasoned about from within itself.

**Thread 2: The writing philosophy**
"Separation of concerns" in CSS was: keep HTML (structure), CSS (presentation), JS (behaviour) separate. The user is noticing something almost opposite here — but it's not actually opposite. It's a *different* separation: separate what LLMs already know from what is specific to this codebase.

Traditional documentation assumes zero prior knowledge → verbose.
LLM-era documentation can assume vast prior knowledge → only document the delta.

The delta is: this repo's specific philosophy, patterns, systems, and conventions. Everything else (what Bun is, how git works, what a REST API is) — skip it. LLMs have it.

Calling this **delta documentation**: write only what isn't in the training data. State only the atypical. The test: would a competent LLM already know this? If yes, don't write it.

**Thread 3: Does this need acronyms?**
User asked if the concepts need acronyms. I said CORD (Code-Owned Reflexive Documentation) for the system and delta documentation for the writing style. User then said drop the acronym requirement. Right call — acronyms are a crutch. The concepts are clear enough without them. "Reflexive documentation" and "delta documentation" are precise and self-explanatory.

**What the user is really asking for long-term:**
Not just naming — they want this captured as a design principle that future agents can use. The principle should live in PHILOSOPHY.md, not just AGENTS.md. AGENTS.md is operational. PHILOSOPHY.md is the *why*. This belongs there.

## The refined formulation (Zilla, 2026-03-20)

> Autopoietic homoiconicity: a system whose documentation is its infrastructure — reading itself to maintain itself, maintaining itself by being read. The documentation is written as compressed delta: it states only what diverges from patterns the reading agent already knows from training data or experience. Everything standard is omitted. Everything specific is stated once, precisely, where it's needed. This compression is made safe by the autopoietic loop — gen scripts produce docs, docs link back to their generators, the system self-discovers and self-updates — guaranteeing the delta never drifts from reality.

## What the system actually is

The gen scripts declare their own metadata via comment headers (`@watches`, `@output`, `@run`). Their outputs carry back-links to their generators (`<!-- AUTO-GENERATED by X — do not edit directly -->`). AGENTS.md describes the whole system including itself. doc-sync.sh closes the loop by discovering scripts, grepping their headers, and running only what's stale.

This is a **reflexive documentation system**: the documentation describes its own creation, maintenance, and regeneration. Two-way links between generators and outputs. Self-registering via convention rather than central manifest. No manual registration anywhere.

Closest concepts in existing canon:
- **Autopoiesis** (Maturana/Varela) — a system that produces the components that constitute it
- **Reflexive systems** — systems that can examine and describe themselves
- **Closed-loop documentation** — vs open-loop (code changes, docs don't follow automatically)
- **Homoiconicity** (Lisp) — code is data; here, docs describe the system that produces them

The writing philosophy is **delta documentation**: assume LLM training data as baseline, document only the delta — what's specific to this repo, this philosophy, this system. The test for any sentence: "would a competent LLM already know this?" If yes, cut it.

## Audit: does the system actually embody its own principle?

*Reading every CAPS file, every gen script, every generated output through the autopoietic homoiconicity lens. Probing gaps.*

### The better prompt (delta-compressed version of what was asked)

> Audit all CAPS files and gen scripts against the autopoietic homoiconicity principle: (1) identify every place the system describes a link that doesn't exist, (2) identify every sentence that fails the delta test, (3) identify every gap in the two-way link system between CAPS files and their generated outputs. Then design a `doc-health.sh` script that measures these properties automatically, establishing axes of assessment that could drive an autoresearch loop. The script should use only the system's own self-describing properties (`@watches`, `@output`, `<progressive-disclosure>` tags, `AUTO-GENERATED` headers) as its measurement tools — no external dependencies.

### Gap 1: The two-way link system is ~80% complete

**What exists:**
- CAPS files → generated outputs (via `<progressive-disclosure><output>` tags) ✓
- Generated outputs → their generators (via `<!-- AUTO-GENERATED by X -->`) ✓
- Gen scripts → their outputs (via `@output` header) ✓

**What's missing:**
- Generated outputs ↛ their parent CAPS file

COAT.md knows who generated it. It doesn't know it's referenced in `ARCHITECTURE.md §COAT`. If an agent opens COAT.md cold, they have no path to the CAPS file that contextualises it.

**Fix:** add `@parent` to gen script headers and `<!-- Parent: CAPS_FILE §section -->` to generated output headers. Closes the loop fully.

```
<!-- AUTO-GENERATED by scripts/gen-integration-surface.ts — do not edit directly -->
<!-- Watched: src/services/control-api.ts, src/core/command-catalog.ts -->
<!-- Regenerate: bun scripts/gen-integration-surface.ts -->
<!-- Parent: ARCHITECTURE.md §COAT — Command Once, Adapt Thin -->
```

### Gap 2: `@watches` granularity is uneven

- `gen-COAT.ts` watches specific files: `src/services/control-api.ts src/core/command-catalog.ts` ✓ precise
- `gen-skills.py` watches a directory: `.pi/skills/` ✓ correct, skills are a dir
- `gen-primitives.ts` watches `src/core/` — this is broad. Any change to any core file triggers regeneration, including unrelated changes. Should it watch `src/core/*/index.ts` specifically?

**Fix:** tighten `gen-primitives.ts @watches` to `src/core/*/index.ts` — only index files affect the primitives barrel.

### Axes for autoresearch / doc-health.sh

These are measurable automatically using only the system's own self-describing properties:

| Axis | Measurement | Tool |
|------|-------------|------|
| **Staleness** | Do committed outputs match what gen scripts would produce? | `doc-sync.sh --check` exit code |
| **Header completeness** | Do all gen-* scripts have `@watches`, `@output`, `@run`? | grep each `scripts/gen-*` |
| **Back-link completeness** | Do all generated files have all 3 `<!-- -->` header lines? | grep each `@output` target |
| **Forward-link completeness** | Do generated files have `<!-- Parent: -->` header? | grep each `@output` target |
| **Progressive-disclosure integrity** | Does each `<output>` file in CAPS files actually exist? | find each path in `<output>` tags |
| **@watches precision** | Are any `@watches` paths directories when specific files would suffice? | heuristic: flag dirs with `*/` |
| **Delta score** | What % of sentences in CAPS files contain standard LLM knowledge? | LLM-as-judge, 0–10 per sentence |

First 6 are mechanically checkable. The 7th (delta score) requires an LLM judge — but that's the most valuable one and the most novel: using an LLM to score whether documentation is appropriately compressed for an LLM reader.

---

### The autoresearch loop design

Primary metric: composite doc-health score (0–100).
- Axes 1–6: 10 points each (60 points mechanical)
- Axis 7: 40 points (LLM judge, average delta score across all CAPS sentences)

Loop:
1. Run `doc-health.sh` → score
2. Identify lowest-scoring axis
3. Make targeted improvement (fix a header, tighten a `@watches`, cut a non-delta sentence)
4. Re-score → keep if improved
5. Repeat

The loop uses the system's own self-describing properties as its measurement instrument. The system audits itself using itself. That's autopoietic homoiconicity applied to quality assurance — the principle eating its own tail.
